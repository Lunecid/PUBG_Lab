이 문서는 저자(백성은)가 준 규칙을 한곳에 모은 것이다. 설계·데이터·학습·문헌·기록 작업을 시작하기 전에 읽는다. 저자가 새 규칙을 주면 같은 날 이 문서와 변경 기록(맨 아래)을 고친다. 다른 프로젝트에서 다시 쓸 재사용판은 `docs/guidelines/`에 있다.

표기: 각 규칙 끝의 괄호는 출처(날짜, 저자 원문)다. **[해석]** 표시는 저자의 일반 원칙을 구체 항목으로 풀어 쓴 것으로, 저자 확인 전까지는 제안이다.

## A. 아키텍처 설계 법칙

> "우리는 기계공학자가 됐다고 생각하고 아키텍쳐의 하나하나 설계에 모두 이유와 근거 그리고 물리적 공학적 컴퓨터공학적 법칙에 맞게 효율적이고 아름답게 설계한다" (2026-10-19)

A0. 부품 하나마다 설계 카드를 쓴다: 요구 → 지배 원리 → 문헌 근거 → 우리 데이터 근거 → 선택한 형태 → 시간·메모리 비용 → 반증 시험. 카드가 없는 부품은 넣지 않는다.

아래 A1~A9는 "물리·공학·컴퓨터공학 법칙"을 이 문제에 맞게 푼 것이다. **[해석]**

A1. **대칭**: 알려진 대칭은 데이터로 배우게 두지 말고 구조에 넣는다. 대칭은 게임의 실제 대칭이어야 한다. 예를 들어 팀 교환은 지도 좌표 변환과 함께여야 같은 물리 상태가 된다. 실제로 깨진 대칭(진영 이점 등)은 숨기지 말고 명시적 변수로 둔다.
A2. **보존·회계**: 예측량 사이의 항등식은 출력 구조로 보장한다. 누적 = 구간 합, 순골드 = 두 팀 골드의 차, 확률 합 = 1, 누적량은 단조 증가, 경기가 끝난 뒤에는 사건이 없음.
A3. **인과**: t0 뒤의 정보는 입력에 들어가지 않는다. 모든 특징의 관측 시각은 t0 이하다. 패치·경기 단위 분할 누설도 막는다.
A4. **단위와 척도**: 모든 양의 단위(초, 골드, 지도 좌표 단위, 횟수)를 적는다. 정규화 척도를 고른 근거를 남긴다. 수치 안정 범위(로그 링크, 클리핑)를 정한다.
A5. **정보와 결측**: "관측 안 됨"과 "0"을 구분한다(지원 표시). 결측 자체가 정보인지 확인한다.
A6. **계산**: 부품마다 시간 복잡도와 메모리를 적고 상한(스왑 없이 private 48 GiB) 안에 둔다. 데이터 이동을 줄인다. 결과는 비트 단위로 재현돼야 한다. 비트 재현은 "같은 기준선 안에서" 지킨다: 효율을 위해 계산 방식을 바꾸면(예: 트리 공유 구간화, 스레드 수) 새 기준선으로 정하고 이전 결과는 동결 참조로 남긴다. ("정할 것 1–4 추천대로 간다: 새 트리 기준선(8스레드, T2 공유 구간화, 헤드별 중간 저장) …", 2026-10-19)
A6a. **장치**: 보고용 실행은 CPU로 하고 비트 재현을 지킨다. GPU(RTX 5080)는 하이퍼파라미터·구조 탐색에만 쓴다. GPU 실행은 실행 카드와 자원 기록에 장치, 드라이버, CUDA, 결정성 설정을 남긴다. ("GPU는 탐색에만", 2026-10-19)
A7. **최소 충분 구조**: 요구를 만족하는 가장 단순한 형태를 고른다. 부품마다 제거 실험으로 기여를 확인한다.
A8. **반증 가능성**: 부품마다 "이 결과가 나오면 버린다"는 시험·지표·기준을 미리 적는다.
A9. **아름다움**: 같은 개념에는 같은 연산자를 쓰고, 공유할 수 있는 부품은 공유하고, 예외 처리를 줄인다.

A10. **공학적 최적화**: 모든 연산과 설계는 공학적 최적화에 바탕을 둔다. ("모든 연산과 설계는 공학적 최적화를 바탕으로 한다", 2026-10-19) 아래는 이를 풀어 쓴 것이다. **[해석]**
- 설계 변수, 목적(예측 성능), 제약(메모리 48 GiB, 시간 예산, A1~A3 법칙)을 명시한 최적화 문제로 쓴다.
- 손으로 고른 값 대신 실험 계획(DoE), 민감도 분석, 베이지안·다목적 최적화로 정한다.
- 성능 대 비용의 파레토 앞면을 보고 고른다.
- 연산은 측정(프로파일링)으로 병목을 찾은 뒤 최적화한다.

## B. 진행 방식

B1. 프로젝트(모델 설계)는 아직 확정되지 않았다. 기존 코드와 아키텍처를 먼저 논의한다. ("기존코드에 대한 논의를 먼저해야지 우리가 프로젝트를 확정한게 아니잖아", 2026-10-19)
B2. 학습부터는 단계마다 결과를 보고하고 시각화 자료를 만들어 논의한 뒤 다음 단계로 간다. 긴 실행을 자동으로 이어 붙이지 않는다. ("이제 학습부터 작업할때 단계마다 결과를 보고하고 시각화자료를 만들어서 논의해보자", 2026-10-19)
B3. 설계서를 먼저 보여 주고, 코드는 승인 뒤에 바꾼다. 패치는 적용 전에 보여 준다. ("설계서를 먼저 보여주고, 코드는 내가 승인한 뒤에 바꿔라", "적용 전에 보여줘", 2026-10-19)
B4. 아키텍처 설계 논의가 학습보다 먼저다. ("일단 아키텍쳐 설계에 대한 논의를 먼저해봐야해", 2026-10-19)
B5. 커밋은 요청할 때만, 푸시는 저자 재승인 전에는 하지 않는다. ("푸시와 삭제는 내가 다시 승인할 때까지 하지 마", 2026-10-18; 삭제는 C2로 범위가 정해짐)
B6. 모든 작업은 논문으로 쓸 것을 전제로, 설계·근거·도출을 메모하며 진행한다(데이터 사이언티스트 수준의 엄밀성). (2026-10-05, 메모리 feedback-thesis-first-documentation)
B7. 연구 방향은 C(교전 과정 모형: 교전 발생 hazard + 교전 결과 + 교전 뒤 흐름)다. 모든 세부 설계는 저자 허락을 받는다. 전체 큰 그림을 먼저 그리고 부족한 점을 하나씩 채운다. 학습처럼 오래 걸리는 작업은 전체 설계를 다 마친 뒤에 진행한다. ("C 로 가자. C로 가되 모든 세세한 설계를 다 나에게 허락을 맡고 일단 전체적인 큰 그림을 그리고 부족한 점을 채워나가는 식으로 가자. 그리고 학습이나 여러 시간이 오래걸리는 부분은 전체적인 설계를 다하고 진행하는거야.", 2026-10-19)

## F. 글쓰기와 주장

F1. 주장은 증거만큼만 한다(0을 포함하는 구간 = 미결, 미검출 ≠ 부재 등). (메모리 feedback-restrained-claims)
F2. 학위논문·ToG 원고·발표 덱의 문체 규칙은 각 메모리를 따른다. (feedback-thesis-abstract-style, feedback-tog-widom-style, feedback-seminar-deck-style, feedback-position-check-framing)
F3. **평가 사전 등록**: 결과를 보기 전에 주장마다 판정 방법을 정해 잠근다. ("각 주장마다 주 지표와 주 비교를 지정하고, 나머지는 보조 결과로 두자", "A4의 ‘동등 이상’ 역시 유의한 차이가 없다는 것만으로 입증되지는 않아", 2026-10-20; 승인 "평가 사전 등록안 승인", 같은 날)
- 주장마다 주 비교, 주 지표, 주 자료(지평 포함)를 하나씩 정한다. 나머지는 모두 보조 결과다.
- 같은 변수를 같은 적정 점수로 비교한다. 점 예측과 분포 예측을 맞대면 둘 다 분포로 만들어 같은 점수(예: CRPS)로 잰다. 머리별 NLL 합을 다른 목표를 가진 모형의 손실과 비교하지 않는다.
- 정보 가치와 방식의 우월성을 나눠 잰다. 정보 가치는 같은 모형 안에서 정보만 달리해(다시 학습 없이) 재고, 방식의 우월성은 같은 정보를 주고 방식만 바꿔 다시 학습해 잰다. 공유 인코더를 다시 학습해 생기는 간접 변화는 따로 보고한다.
- 학습 방식(예: 가린 보기 학습)의 효과는 그 방식을 끈 필수 제거 실험으로만 주장한다. 가림이 있다고 누설이 없는 것은 아니므로, 누설은 단위 시험으로 따로 확인한다.
- "적어도 같다"는 결과 전에 잠근 한계 ε로 비열등을 보여야 한다(차이 95% 구간의 위끝 < ε).
- 시드 변동과 경기 부트스트랩을 함께 보고한다: 시드 짝 차이의 평균, 같은 재표본을 모든 시드에 쓴 구간, 모든 시드의 부호 일치, 시드별 점 차이 공개, 주 비교 묶음에 Holm 보정.
- 우연 기준이 있는 탐침(예: 1/3)은 보조 진단이며, 표본 균형이 맞을 때만 그 기준을 쓴다.

## I. 산출물·코드 관리: AI 기업 방식

> "프로젝트 산출물관리 및 전체적 코드 관리는 AI대기업 예를들면 오픈에이아이 앤트로픽이 하는 방식을 따른다." (2026-10-19)

아래는 두 회사가 공개한 자료와 업계에서 널리 쓰는 ML 공학 관행을 우리 규모에 맞게 옮긴 것이다. **[해석]**

I1. **기준 저장소 하나**: 코드·설정·평가 정의·문서는 git 저장소(허브)에 둔다. 무거운 산출물(데이터, 저장소, 모델)은 저장소 밖(`D:\LOL_Data`)에 두고 저장소에는 경로와 해시가 담긴 매니페스트만 둔다.
I2. **에이전트 지침 파일**: 저장소 루트의 `AGENTS.md`(코딩 에이전트용 공개 형식)와 `CLAUDE.md`(Claude Code)가 프로젝트 규칙, 실행·시험 명령을 담고 이 문서를 가리킨다. (출처: agents.md 형식, Anthropic "Claude Code: Best practices for agentic coding")
I3. **변경 흐름**: 설계 문서 → 계획 → 브랜치 또는 worktree → 시험 먼저 → 작은 단위 변경 → 독립 검토 → 병합. 주 브랜치를 직접 고치지 않는다. 커밋·푸시는 저자 승인(B5). (출처: 같은 Anthropic 자료의 탐색-계획-구현-커밋, 시험 주도 흐름)
I4. **실행은 고치지 않는 기록**: 실행마다 날짜 폴더에 카드(설정), 코드 버전(해시), 데이터 해시, 환경 잠금 파일, 결과를 남긴다. 끝난 실행은 고치지 않고, 바꿀 일이 있으면 새 실행을 만든다. 결과 보고는 어느 실행(체크포인트)의 것인지 밝힌다. (출처: OpenAI system card가 결과를 특정 체크포인트로 한정하는 방식)
I5. **고정된 평가 하네스**: 분할, 지표, 신뢰구간 계산을 코드로 고정하고, 모든 변경에 같은 평가를 다시 돌려 회귀를 막는다. (출처: OpenAI Evals, 배포 전 CI에서 평가를 돌리라는 OpenAI cookbook 권고)
I6. **모델 카드와 데이터 카드**: 모델 버전마다 목적, 데이터, 평가, 한계를 적은 카드를, 데이터셋 버전마다 출처·처리·분할을 적은 카드를 둔다.
I7. **버전과 릴리스**: 버전 번호(r1, r2, …), 변경 기록, 해시로 잠근 릴리스. 릴리스 뒤에는 내용을 바꾸지 않는다.
I8. **재현성**: 환경 잠금, 시드, 결정성 시험. 같은 입력이면 비트 단위로 같은 결과.
I9. **보존과 정리**: 실행 색인(날짜, 상태, 보존 여부)을 유지하고, 논의가 끝나면 불필요한 산출물을 지운다(C2). 증거 사슬은 남긴다.
I10. **비밀과 데이터 보호**: 비밀 정보는 코드, 로그, 모델 입력, 외부 서비스에 넣지 않는다(C6).
I11. **코드 안의 논문 인용**: 논문을 근거로 설계한 코드에는 나중에 인용할 수 있도록 그 논문을 주석으로 남긴다. ("논문을 이용해서 설게할경우 후에 인용을 할수있도록 코드에 그 논문의 주석을 남긴다", 2026-10-19) 형식은 아래와 같다. **[해석]**
- `# Ref: <제1저자> et al. <연도>, "<제목>", <게재처>, <식·절·쪽>; <식별자(DOI·arXiv·OpenAlex)>`
- 함수 문서 문자열이나 그 코드 바로 위에 둔다.
- 식을 옮겼으면 식 번호를, 바꿨으면 무엇을 바꿨는지를 적는다.
- 같은 정보를 설계 카드의 문헌 칸에도 남긴다.
I12. **역할별 모델**: 코드 구현과 작은 작업은 Sonnet이나 Haiku 하위 에이전트가 맡고, 과제 검토, 단계 관문 검토, 최종 검토 같은 전체 점검과 품질 관리는 Opus가 맡는다. 하위 에이전트를 부를 때는 모델을 늘 명시한다. ("코드 구현 및 작은 작업들은 SONNET이나 HAIKU로 구현하고 전체적인 점검 및 품질 관리는 OPUS로 진행해", 2026-10-20)

## J. 설명과 설득

> "너가 하는 모든 행위에 대한 근거를 나에게 설득한다고 생각하고 설계서를 항상 알기쉽고 5살 아이에게 설명하는 듯한 느낌의 스킬을 사용해서 설득한다" (2026-10-19)

("5살 설명은 너무 어린애한테 설명하는거같으니까 이걸 이용하되, 데이터사이언스 및 AI 대학원 석사과정에서 박사과정 초입수준으로 설명해줘", 2026-10-19) 쉬운 설명 스킬을 쓴다: `eli5`(말투), `doc-coauthoring`(결정 문서 구조), `feynman`(이해 확인, 요청 시) 설치됨(2026-10-19). 이를 묶는 맞춤 스킬 `eli5-design-memo`(부탁 → 직관 설명 → 근거 꼬리표 붙은 이유 → 법칙 점검 → 반증 실험 → 비용·되돌리기 → 선택지 → 그림)를 설계 메모, 결정·설치 요청, 되돌리기 어려운 행동 전에 쓴다. ("eli5-design-memo 초안대로 설치해라", 2026-10-19; 원본 `D:\LOL_Data\runs\20261019_architecture_review_1\skills_draft\`)
